Executive summary:
  • Current I2C based architecture cannot reliably support 8 IMUs at 100Hz due to EMI, cable length, and clock stretching.
  • Testing confirms real world latency exceeds theoretical limits.
  • I propose moving to a UART + RS-485 architecture using BNO085 IMUs and a Teensy 4.1 as the intermediary.
  • This allows parallel sampling, real time latency, and immunity to electromagnetic interference.
  • Estimated Cost: $288-$318
  • Estimated completion timeframe: 10-25 days depending on approach.

1. Communication Protocol: 

The current communication method being utilized (I2C), has demonstrated several limitations in our use case that could impede reliability:
  • EMI Susceptibility: I2C is designed ideally for short traces on a PCB. There is no immunity to electrical noise. Since the system will be in close proximity to high voltage inductive loads (pneumatic solenoids, relays, power systems), the I2C bus is at significant risk of electromagnetic interference. My concern is this potentially leading to data corruption and instability.
  • Cable Length Constraints: I2C has a very restricted maximum cable length. Running cables completely down the leg can exceed rated specifications and cause signal degradation. I integrated protective measures such as several pull up resistors to try and account for this, but this is still a significant weak point in the current system.
  • Multiplexing Latency: Since all the IMUs shared the same address, a multiplexer was required. A down side of this approach is some latency is unavoidable and the readings are never sequential. There is always going to be some amount of spacing in between sensor readings because of the functionality of the multiplexer.

After further research on the potential alternatives, I found UART with RS-485 to be by far the most reliable communication protocol for this use case:
  • Industrial Noise Immunity: Using RS-485 transceivers, the UART signal is converted into differential signaling. This method causes the system to reject noise generated by other systems such as the solenoids or power systems. This ensures that there can be viable data collected in a high EMI environment.
  • Consistent Long Distance Communication: RS-485 is an industrial standard for maintaining signal integrity rated for cables over 100 meters, this far surpasses what would be needed for the IMU system and resolves any concern for signal degradation.
  • Simplified wiring setup: This approach allows for point to point connections with a primary microcontroller (Teensy 4.1), removing the need for a multiplexer.

2. IMU Selection:

To achieve the target 100Hz sampling rate and eliminate data bottlenecks, I recommend upgrading from the current BNO055 to the BNO085. While the BNO055 is a capable general purpose sensor, the BNO085 is its successor intended specifically for robotics applications where low latency is essential.

3. Bandwidth and Latency Re-Evaluation:

3.1 Previous Theoretical Model (I2C)
Initial calculations for the current system suggested that a 100Hz sampling rate was achievable using a 400kHz I2C bus.
  • Data Payload: 306 bits per sensor (Quaternions + Raw Data)
  • Total Throughput: 306 bits x 8 sensors x 100 Hz = 244,800 bps
  • Bus Utilization: On a 400kHz bus, this demands 61% utilization
  • Theoretical Latency: The calculated time to scan all 8 sensors was 2.34 ms
Why this model failed when applied in the real system: While still valid for ideal data transmission, the model did not account for clock stretching. I found that the BNO055 is known to clock stretch for 1-3 ms while processing the fusion algorithm.
  • True Latency accounting for clock stretching: 2.34 ms (Transfer) + (8 sensors x 2 ms Wait Time) = 18.34 ms.
  • This concludes that the time to read one frame (18.34 ms) goes past the 10 ms window needed for 100Hz. This further verifies what I found in my testing over the weekend.
3.2. New Theoretical Model (UART)

With this different protocol being acquired, we use the same data payload as the previous system (306 bits) to show the difference in efficiency.
  • Proposed Bus Speed: 921,600 bps (Standard for High Speed UART)
  • Parallelism: All 8 sensors transmit simultaneously on their own dedicated lines
Latency Calculation: Because all 8 sensors operate at the same time with no interval in between, only one sensor needs to be calculated for. 

While the Teensy's hardware is theoretically capable of 6MHz or 6,000,000 bps, it is standard practice to choose 921,600 to ensure signal stability.

Min Latency (Theoretical Max Bus Speed) = 306 bits / 6,000,000 bps = 0.051ms

4. Wiring arrangement:

Right now, the setup has been to directly connect a Raspberry Pi 4 to an I2C multiplexer, which then branches off into the 8 IMUs:



I propose that we separate the systems by connecting the IMUs to a microcontroller with a high processing speed, such as a Teensy 4.1, and then having the microcontroller interface with the Raspberry Pi over serial: 



This approach will offload significant strain on the Raspberry Pi, and as the gait detection algorithm can potentially get more sophisticated in the future that additional room for processing may be deemed beneficial. Additionally, having separate systems that are dedicated to performing fewer tasks is a good approach to minimize potential points of failure. 

5. Cost Breakdown:

Regarding the costs, there are two options depending on the time frame that this would ideally need to be done in. The PCB does not have to be redesigned. I have a way to modify one of the non-populated boards and hand-wire the new connections/components. This approach would be functional and get a working system much sooner. If a new PCB is designed and manufactured, the process to design it won't take long; however, there may be higher costs and wait times depending on the manufacturing service. Additionally, with the PCB approach, the overall IMU System may end up taking up less space due to the optimized routing and low profile. Because we ordered extra components from Mouser/Digikey, there would be no need to order additional components from them either. I see the PCB as a much more professional-looking iteration, but the decision depends on what the current priority is.
